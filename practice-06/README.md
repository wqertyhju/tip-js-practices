## Цель и результат

Цель — связать браузерное приложение с HTTP API, реализовать создание, редактирование, удаление и фильтрацию задач через сервер, а также обеспечить устойчивость интерфейса к асинхронным ошибкам и гонкам запросов.

Получен полностью рабочий браузерный клиент, который:
- загружает задачи и категории с учебного API;
- создаёт, редактирует, удаляет задачи и меняет их статус через запросы;
- отображает состояния `loading`, `ready`, `empty`, `error`;
- защищён от устаревших ответов при быстрой смене фильтров;
- безопасно выводит серверные данные как текст (через `textContent`).

## Устройство HTTP-клиента

Файл `src/api-client.js`:
- `buildUrl` — сборка URL с query-параметрами через `URLSearchParams`.
- `createApiClient` — фабрика, принимает `baseUrl`, `fetchFn`, `timeoutMs`.
- `requestJson` — выполняет GET, POST, PATCH, DELETE, проверяет `Response.ok`, `Content-Type`, разбирает JSON, возвращает `null` для 204.
- Ошибки классифицируются через `ApiError` с полем `kind`: `http`, `network`, `invalid-response`, `timeout`, `aborted`.

## Устройство предметного API

Файл `src/task-api.js`:
- `getTasks(filters)`, `getTaskById(id)`, `getCategories()`, `loadInitialData(filters)`;
- `createTask(draft)`, `updateTask(id, changes)`, `setTaskCompleted(id, completed)`, `deleteTask(id)`, `resetDemoData()`;
- проверяет схему ответа и уникальность id, возвращает `ApiError` при неверной схеме.

## Схема асинхронных состояний

| Состояние | Когда | Что показывает интерфейс |
|-----------|-------|--------------------------|
| loading | Ожидание ответа | Текст «Загрузка...», `aria-busy="true"` |
| ready | Получен непустой список | Карточки задач, сводка |
| empty | Запрос успешен, задач нет | Сообщение «Задач по выбранному фильтру нет» |
| error | Ошибка запроса | Сообщение об ошибке и кнопка «Повторить» |

## Защита от устаревшего ответа

В `app-controller.js` реализованы два механизма:
1. При новом запросе предыдущий отменяется через `AbortController`.
2. Каждому запуску присваивается номер `seq`, и результат применяется только если номер совпадает с последним.

Это гарантирует, что быстрая смена фильтров не приведёт к отображению устаревших данных.

## Индивидуальный сценарий (вариант 3)

Начальный фильтр: `priority: "high"`.
1. При загрузке отображаются задачи с высоким приоритетом (3 штуки).
2. Создание задачи с приоритетом `medium` — карточка **не появляется** в текущей выборке (так как фильтр `high`).
3. Изменение приоритета видимой задачи на `medium` — карточка исчезает из выборки (подтверждено в браузерных проверках).
